# Technical Requirements Document (TRD) — CopyDash

> Reflects the actual stack and architecture already running in `elilisaehr/CopyDash`, not a proposal.

## Platforms

Web only. Responsive breakpoints are not formally audited — the UI is built with inline pixel-based styles ported from a desktop design prototype; small-screen behavior should be checked before relying on it.

## Frontend and hosting

- **Next.js 16** (App Router, TypeScript, Turbopack dev/build). Note: Next.js 16 has breaking changes from earlier versions (async `params`/`searchParams`, etc.) — see `AGENTS.md` at the repo root, which is regenerated by `next dev` and should stay committed.
- **Tailwind CSS v4** is installed and provides the base reset/tokens (`app/globals.css`), but most UI is written as **inline styles**, deliberately ported 1:1 from the original design prototype's exact pixel/hex values rather than Tailwind utility classes.
- **Hosting: Vercel**, auto-deploying from the GitHub repo's `main` branch. Server functions are pinned to **`fra1` (Frankfurt)** by `copydash-app/vercel.json`, next to the prod database — Vercel's default (`iad1`, Washington) made every query cross the Atlantic.
- **No `middleware.ts` / `proxy.ts`** is present. One was tried and caused a Vercel Edge-runtime crash (`MIDDLEWARE_INVOCATION_FAILED`); route protection was moved entirely into Server Components instead (see "Authentication and roles" below). This is a real, deliberate current-state decision, not an oversight — keep in mind if re-introducing middleware later.

## Backend and database

- **Supabase**: Postgres (schema + Row Level Security), Auth (email/password only — no OAuth/social login), Storage (private `pdfs` bucket for uploaded PDF designs).
- Single Supabase project / single environment today — no separate staging project.
- Region: prod Supabase is in **AWS eu-central-1 (Frankfurt)**, the dev project in eu-west-1 (Ireland). If prod ever moves, move the Vercel function region in `vercel.json` with it.

## Authentication and roles

- Supabase Auth, email/password sign-up and sign-in.
- Role (`pm` or `client`) is chosen at sign-up, stored in the user's `user_metadata`, and copied into a `profiles` row on first login (`lib/auth.ts: ensureProfile`).
- **Route protection is enforced independently in each route group's `layout.tsx`** (`app/pm/layout.tsx`, `app/client/layout.tsx`) as a Server Component: it reads the session, redirects to `/login` if absent, and redirects to the other role's home if the role doesn't match. There is no middleware-level gate — this is intentional (see above) but means protection is duplicated per layout rather than centralized.
- A client is auto-linked to a PM's project via a Postgres trigger that matches the signing-up client's email against any `client_emails.address` row (case-insensitive) — see Backend Schema doc.

## Architecture

- **Server Components** fetch data via `lib/supabase/server.ts`'s `createClient()` (runs as the signed-in user, respects RLS) or `createAdminClient()` (service-role key, server-only, bypasses RLS — currently only wired up, not actually called anywhere in the app yet).
- **Data-fetching rules (speed)**: `createClient()`, `getUser()` and `getProfile()` (`lib/auth.ts`) and `getWorkspaceContext()` are memoized per request with React `cache()`, so a layout and its page verify the session and load the profile/workspace once. In pages, start independent queries together with `Promise.all`, and pull related rows in the same request with PostgREST embeds (e.g. `projects.select("*, pages(status)")`) instead of a second round trip. `app/pm/loading.tsx` and `app/client/loading.tsx` show a skeleton instantly while a page loads.
- **Client Components** mutate data via `lib/supabase/client.ts`'s browser `createClient()`, then call `router.refresh()` to re-fetch server data rather than managing client-side cache.
- **PDF pipeline is 100% client-side**: `lib/pdf.ts` loads pdf.js (with its worker), `lib/pdf-design.ts`'s `buildBlocks()` groups extracted text items into editable "blocks" by geometry (font size, line spacing, horizontal overlap — a heuristic, not ML), and renders the page to a canvas image that the text overlays sit on top of. Nothing about PDF content is ever sent to a server.
- **Figma pipeline is server-side** for the API call (`app/api/figma/import/route.ts`, `app/api/figma/connect/route.ts`) specifically so the PM's Personal Access Token never reaches the browser; the fetched blocks + a rendered PNG URL are then stored in `figma_designs` and rendered client-side with the exact same `EditableBlock` component the PDF path uses.
- **File storage**: uploaded PDFs go to Supabase Storage's `pdfs` bucket, path-scoped per project (`{project_id}/...`) so RLS can check access by folder name.

## Security and privacy

- Every table has Row Level Security scoping data to the owning PM (`pm_id = auth.uid()`) or to project members (`is_member_of_project()`). See the Backend Schema doc for the full policy list.
- The `pdfs` Storage bucket is **private**; access is RLS-gated the same way as the database rows.
- **Known gap**: the Figma Personal Access Token is stored as plaintext in `figma_connections.access_token`. It's protected by RLS (only the owning PM's server-side requests can read it, and only server code ever sends it to Figma), but it is not encrypted at the column level. **[OPEN QUESTION]** — is this acceptable, or does it need column-level encryption / a secrets manager before handling real customer tokens at scale?
- No formal data retention or deletion policy exists yet (see Backend Schema doc, "Retention and deletion" — **[OPEN QUESTION]**).
- No sensitive-data classification has been done (e.g., is client contact info "PII" requiring special handling under your jurisdiction's law) — **[OPEN QUESTION]**.

## Performance and reliability targets

None formally set. **[OPEN QUESTION]** — suggested defaults to adopt unless you want something stricter: page loads under ~2s on a typical connection, Vercel's standard platform uptime (no custom SLA), no formal backup policy beyond Supabase's own point-in-time recovery (confirm your Supabase plan includes it).

## Environments and delivery

- **One environment**: production only, on Vercel, tracking the GitHub repo's `main` branch. No staging/preview environment is currently used as part of the workflow.
- **No CI/CD pipeline** — no automated test run, lint, or type-check happens before a deploy; Vercel builds whatever lands on `main`.
- **No automated tests exist** (unit, integration, or end-to-end).
- Current delivery process has been manual (upload a zip of changed files through GitHub's web UI) because of how this project's early development sessions were set up — **this should change** once you're working from VS Code/Cursor with normal `git push` access; there's no technical reason to keep doing manual uploads going forward.

## Key technical decisions and tradeoffs

| Decision | Reason | Alternative considered |
|---|---|---|
| Inline styles instead of Tailwind utility classes for most UI | Pixel-exact port of an existing design prototype (exact hex/pixel values) | Rebuild all UI in Tailwind utilities — more idiomatic/maintainable long-term, but was out of scope for matching the prototype exactly |
| PDF processing entirely client-side (pdf.js) | No server infrastructure/cost for rendering; works offline-ish once loaded | Server-side PDF rendering (e.g. a headless-Chromium or poppler service) — more consistent output, but adds infrastructure and cost |
| Geometry-based heuristic to detect paragraphs in a PDF (font size + line spacing + horizontal overlap), not an ML/OCR layout model | Fast, no external dependency, works well on structured/typeset PDFs (verified against a real newsletter export) | A proper layout-analysis model — more robust on irregular PDFs, but much higher complexity/cost for marginal gain at this stage |
| No `middleware.ts`; route protection duplicated in each layout's Server Component | A middleware version crashed specifically on Vercel's Edge runtime | Fix the Edge-runtime middleware instead — would centralize the logic, but wasn't resolved in the time available; worth revisiting |
| AI features fully mocked behind one module (`lib/ai-mock.ts`) | Lets the whole UX (loading states, suggestions, "extract from PDF") be built and tested without needing or paying for a real model yet | Wire a real model from day one — more "real," but adds cost/complexity before the UX was validated |
